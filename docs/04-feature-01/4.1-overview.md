# Feature 1 – SQL‑Queryable Experiment Runs

## Goal
Make RunLedger the first lightweight artifact registry where you can **query your experiment history using raw SQL power** — directly through the API, without writing scripts that crawl a folder of JSON files. This feature brings the “Q” in “Queryable” to life.

## What it will do
1. **List all runs** with pagination and sorting (`GET /api/runs`).
2. **Filter runs by metric thresholds** — e.g., “show me all runs where `asr` < 0.1 and `balanced_utility` > 0.9”.
3. **Full‑text phrase search** across the entire JSON payload or within a specific field (e.g., `config.merge_method`).
4. **Fuzzy search** for approximate string matches (e.g., “weight averaging” matching “weighted averaging”).
5. **Combine text and metric filters** in a single request.
6. **Return results as clean, paginated JSON** using the existing `RunResponse` DTO.

All of this works by translating request parameters into **PostgreSQL JSONB queries** inside the repository layer — no additional infrastructure required.

## What we have now (pre‑conditions)
- Working `run` table with `id`, `payload` (JSONB), and `created_at`.
- Flyway migration `V1__create_run_table.sql` applied.
- `POST /api/runs` and `GET /api/runs/{id}` endpoints fully functional.
- `Run` entity, `RunRepository` (currently only basic CRUD), `RunController`, `RunRequest`/`RunResponse` DTOs.
- `ObjectMapper` available as a Spring bean.
- PostgreSQL 16 running with `jsonb` support (no extra extensions required for metric filtering; full‑text search and fuzzy matching will use built‑in `tsvector` and `pg_trgm`).

## What we need to add

### Database layer
No schema changes are strictly necessary for metric filtering, because `jsonb` operators can extract values on the fly.  
For **performance** we may add:
- A GIN index on the `payload` column for faster JSON queries (e.g., `payload->'metrics'->'asr'`).
- A GIN trigram index for fuzzy search on specific fields (added in a later micro‑iteration, not required for MVP).

A new Flyway migration **V2__add_query_indexes.sql** is optional but recommended once the query features stabilise. For now, we can start without indexes and add them later.

### Repository layer
Extend `RunRepository` with **custom query methods**:
- `findAll(Specification<Run> spec, Pageable pageable)` — using Spring Data JPA Specifications for dynamic, composable filters.
- Alternatively, a custom repository fragment with native SQL that builds a dynamic `WHERE` clause based on request parameters.
- Methods for full‑text search (using PostgreSQL’s `jsonb_to_tsvector` and `phrase_to_tsquery`) and fuzzy matching (using `similarity()` from `pg_trgm`).

We’ll use a **`Specification`** approach initially because it integrates cleanly with pagination and sorting.

### Service layer: `RunQueryService`
A new `@Service` that:
- Accepts query parameters (list of metric filters, text search, fuzzy flag, pagination).
- Constructs the appropriate `Specification` or delegates to repository methods.
- Returns a `Page<Run>` that the controller can map to `Page<RunResponse>`.

### Controller updates
- Add `GET /api/runs` endpoint with query parameters:
    - `metricKey`, `metricValue` (repeatable pairs, e.g., `?metricKey=asr&metricValueLt=0.1&metricKey=balanced_utility&metricValueGt=0.9`).
    - `q` – full‑text search phrase.
    - `qField` – (optional) dot‑separated path to a specific JSON field for search.
    - `fuzzy` – boolean flag for trigram similarity.
    - `page`, `size`, `sort` – standard pagination and sorting.
- Map each `Run` entity to `RunResponse` and return a paginated response.

### DTOs
- `PageResponse<T>` (generic pagination wrapper, or use Spring’s `Page<T>` directly — but a custom one can avoid exposing Hibernate details).
- `RunQueryRequest` (optional, if we want to support POST‑based complex queries later; initial version uses simple GET parameters).

### Exception handling
- Invalid metric keys (non‑existent JSON paths) should return 400 with a clear error.
- Invalid pagination parameters (negative page size) should return 400.
- Empty result sets return 200 with an empty page.

## Why this design
- **JSONB native power:** PostgreSQL’s `->>` and `@>` operators are fast and flexible. We leverage them directly instead of building a separate metadata table, keeping the schema minimal.
- **Specifications for composability:** Spring Data JPA Specifications allow combining multiple filter conditions (metric thresholds, text search, fuzzy) without writing a monolithic query method.
- **Full‑text search and fuzzy matching:** PostgreSQL’s built‑in `tsvector`/`tsquery` and the `pg_trgm` extension cover all our needs without external tools like Elasticsearch.
- **No Python SDK:** Users query directly via the API — language‑agnostic.
- **Scales for interviews:** This demonstrates advanced database skills, dynamic query building, and clean API design.

## Verification strategy
- **Integration tests** with Testcontainers:
    - Ingest several runs with different metric values.
    - Query with `?metricKey=asr&metricValueLt=0.1` → verify correct subset.
    - Query with multiple metric filters → verify AND logic.
    - Full‑text search with exact phrase → verify match.
    - Fuzzy search → verify approximate match.
    - Combine text and metric filters → verify both constraints applied.
    - Test pagination and sorting.
- **Unit tests** for `RunQueryService` with mocked repository (optional, but good for interview).
- Manual testing via PowerShell `Invoke-WebRequest` for quick feedback.

## Completion criteria
- [ ] `GET /api/runs` returns all runs with pagination.
- [ ] Metric filtering works (single and multiple conditions).
- [ ] Full‑text phrase search works (with and without field scope).
- [ ] Fuzzy search returns approximate matches.
- [ ] Filters can be combined.
- [ ] Proper error handling for invalid parameters.
- [ ] Tests pass for all query types.
