# Feature 1 – Tamper-Evident Integrity Chain

## Goal
Make RunLedger cryptographically tamper‑evident. Once a run is ingested, any later modification of its stored data must be **provably detectable**. This is the differentiator that separates RunLedger from every other lightweight experiment tracker.

## What it will do
1. **Assign a content hash to every run** at ingestion time (SHA‑256 of the canonical payload).
2. **Link each run to its immediate predecessor** inside the same experiment by storing the predecessor's hash.
3. **Provide an integrity verification endpoint** (`GET /api/runs/{id}/integrity`) that replays the chain from the first run up to the requested run and confirms:
    - The content hash of each run matches the stored hash.
    - The `previous_hash` of each run matches the hash of the run that came before it.
4. **Return a clear, machine‑readable integrity report** (JSON) that says whether the chain is intact or where the first break occurred.
5. **Prove tamper‑resistance by construction:** because the hash of run *N* depends on the hash of run *N‑1*, altering any run’s data changes its hash, which breaks the link to the next run. The entire chain collapses.

## What we have now (pre‑conditions)
- A working `run` table (`id BIGSERIAL PRIMARY KEY`, `payload JSONB NOT NULL`, `created_at TIMESTAMP`).
- Flyway migration `V1__create_run_table.sql` applied.
- `POST /api/runs` ingestion endpoint that stores arbitrary JSON.
- `GET /api/runs/{id}` retrieval endpoint.
- `Run` JPA entity, `RunRepository`, `RunController`, `RunRequest`/`RunResponse` DTOs.
- `ObjectMapper` available as a Spring bean.

## What we need to add

### Database layer
A new Flyway migration (`V2__add_hash_chain_columns.sql`) that adds two columns to the `run` table:
- `run_hash` – `CHAR(64) NOT NULL` (stores the hex‑encoded SHA‑256 digest of the run’s content).
- `previous_hash` – `CHAR(64)` (nullable; the hash of the previous run; `NULL` for the very first run of an experiment).

Both columns are fixed‑length hex strings (64 chars) for efficiency and readability.

### Entity update
Modify `Run.java`:
- Add fields `runHash` (`String`, length 64) and `previousHash` (`String`, length 64, nullable).
- These fields are set **before** the entity is persisted, not auto‑generated by the database.

### New service: `HashChainService`
A dedicated Spring `@Service` class that:
- Computes a canonical representation of the run’s content (payload as a JSON string, normalized).
- Produces the SHA‑256 hash of that canonical representation.
- Retrieves the last persisted run (by `id`, ordered by insertion) to obtain its `runHash` for use as the `previousHash` of the new run.
- Handles the edge case where there is no previous run (first run of an experiment — `previousHash` left `null`).

### Updated ingestion flow (controller or service)
The `POST /api/runs` handler (or a new `RunService` layer) will:
1. Accept the JSON payload as before.
2. Call `HashChainService` to compute the hash and determine the `previousHash`.
3. Set both fields on the `Run` entity before saving it.
4. Return the normal `RunResponse`; integrity fields are not exposed in the basic response (they are accessible via the integrity endpoint).

### New endpoint: `GET /api/runs/{id}/integrity`
- Retrieves all runs from the first one up to the one with `id`.
- Re‑computes each run’s hash from its stored payload.
- Checks that the stored `run_hash` matches the recomputed hash.
- Checks that the `previous_hash` of each run (except the first) matches the `run_hash` of the previous run in the sequence.
- Returns an `IntegrityReport` DTO containing:
    - `valid` (boolean): true if the entire chain is intact.
    - `runsChecked` (int): number of runs in the chain.
    - `firstBrokenRunId` (Long or null): ID of the first run where verification failed, if any.
    - `details` (list of per‑run status objects, optional).

### New DTO: `IntegrityReport`
A `record` with the fields described above.

### Exception handling
- If the hash computation fails due to a corrupted payload, the ingestion should fail with a 400 or 500.
- The integrity endpoint returns 200 with `valid: false` if the chain is broken; it does **not** throw an exception because a broken chain is a valid (albeit alarming) state.

## Why this design
- **Simplicity:** A linked hash chain is easy to implement, easy to explain, and provides strong integrity guarantees for a sequential log of runs.
- **No external dependencies:** We use only `java.security.MessageDigest` (SHA‑256) – no third‑party crypto libraries required.
- **Performance:** Hashing is fast; chain verification for hundreds of runs will be well under a second.
- **Upgrade path:** Later we can extend this to Merkle trees, Ed25519 signatures, or cross‑experiment links without breaking the existing data model.

## Verification strategy
- **Unit test** `HashChainService`: verify that hash is deterministic, that `previousHash` is correctly set, and that edge cases (first run, empty payload) are handled.
- **Integration test** with Testcontainers:
    - Ingest two runs, verify that the chain is valid via the integrity endpoint.
    - Manually corrupt a run’s payload in the database, then verify that the integrity endpoint reports `valid: false` and identifies the broken run.
    - Test retrieval of integrity for a non‑existent run (expect 404).
